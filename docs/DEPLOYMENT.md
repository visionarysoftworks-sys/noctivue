# DEPLOYMENT.md — Deployment Conventions (Draft)

This draft proposes how the M4 reference app (`examples/reference-crud`)
moves through a documented pipeline — build, test, containerize, deploy —
toward the Phase 6/M5 exit criteria (`docs/IMPLEMENTATION_PLAN.md` §8 and
§8.4). It resolves no open decision; conflicts with Confirmed docs fail
toward the Confirmed text until an ADR amendment lands (`docs/DECISIONS.md`
§1–§2).

## 1. Reproducible builds: the lock is the build input

- The build input is the checked-in pair `nestpkg.nvpm` + `nestpkg.lock`
  (ADR-017; `docs/TOOLCHAIN.md` §3). The lock is generated by
  `noct add` / `noct build`, machine-generated and human-readable.
- CI and release builds MUST resolve from the lock, never re-resolve from
  manifest ranges. Manifest-vs-lock-vs-cache drift MUST fail loudly before
  compilation starts (the enforcement posture recorded in the ADR-017
  amendment); rebuilding silently against newer satisfying versions is
  rejected.
- The gate order is fixed: `noct fmt --check`, `noct lint`, `noct test`,
  then `noct publish --dry-run`. Containerize only what passed all four;
  `noct audit` rows travel with the build report (vulnerability data itself
  is Phase 6 work, `docs/PHASE5_PRODUCTION.md` §6).

## 2. Native binaries and the static-footprint goal

- Release artifacts are native binaries produced by `noct build`
  (Cranelift first, LLVM as the later optimizing backend per ADR-003).
- Goal (not yet a threshold): a static, minimal-footprint binary carrying
  the app and its closed dependency set, with no toolchain, registry
  cache (`.noct/`), or source tree inside the runtime image.
- No new runtime assumption ships through this document: the M4 floor is
  the blocking-threads server plus task-local SQLite pools
  (`docs/PHASE5_PRODUCTION.md` §§1–2). Tuning numbers are recorded, never
  thresholded, until Phase 6 says otherwise.

## 3. Containers

- Base images SHOULD be minimal and pinned by digest. Containers MUST run
  as a non-root user; the image MUST NOT embed secrets, key material
  (`NOCT_SIGNING_KEY`, `NOCT_KEY_ID`), or registry credentials.
- The reference app listens on one configured port (18080 by default;
  `app_port` in `examples/reference-crud/lib/main.nv`) and exposes its
  health as an ordinary read: `GET /health`-style checks against the same
  route table the app serves (`docs/PHASE5_PRODUCTION.md` §5 precedent:
  readiness is a route, not a privileged probe). Orchestrators SHOULD poll
  that route for liveness and readiness.
- Shutdown is graceful drain, not drop. On SIGTERM the supervisor MUST
  stop routing new traffic, then let the app finish in-flight requests to
  response-completion before exiting — the container form of
  `http_server_stop` semantics (`docs/PHASE5_PRODUCTION.md` §2: stop
  accepting immediately, drain accepted connections, return only after all
  connection tasks join). The platform stop-grace period MUST exceed the
  app drain budget; drop-on-stop is rejected for the same reason it is
  rejected in M4 (every deploy becomes client-visible failures).
- No orchestrator-specific mandate: this document requires no Kubernetes,
  no vendor sidecar, and no proprietary agent. Any platform honoring the
  three rules above (non-root, health-route polling, SIGTERM drain) is
  conforming.

## 4. Configuration: env files and process-wins

- Configuration travels as environment. `*.nv.env` files
  (`app.nv.env`-style) are dotenv-compatible `KEY=VALUE` with blank lines
  and `#` comments skipped (ADR-017). `noct run` auto-loads `./*.nv.env`
  in sorted order; an explicit `--env-file` overrides the path.
- The process environment always wins over file values
  (`stdlib/env/dotenv.nv`; `noct-cli/tests/env.rs` precedent). Deploy-time
  injection (orchestrator env / secret store) therefore overrides any
  file-baked default without rebuilding the image.
- Secrets MUST NEVER be committed (`.gitignore` guidance ships with the
  feature per ADR-017). Images contain no secrets; every secret arrives at
  deploy time through the platform, never through the lock, manifest, or
  dotenv file.

## 5. Logs and sinks

- The app logs through the `log/log.nv` facade. `NOCT_LOG` sets the minimum
  level (default `INFO`; unknown values fall back to `INFO`).
  `NOCT_LOG_SINK` selects the sink (`stderr` default; `stdout` for tests
  and golden transcripts). M4 lines are `[LEVEL] message` with no
  timestamps by design (goldens pin them); structured timestamps,
  correlation IDs, and OTel export arrive as Phase 6 observability
  (`docs/IMPLEMENTATION_PLAN.md` §8.1) and are not promised here.
- Operators wire the sink, not the format: attach the container stdout /
  stderr stream to the platform collector. No file-path or rotation
  contract is specified in this draft.

## 6. What operators MUST NOT expect yet

- **TLS:** the M4 server is plaintext-only and the client refuses
  `https://` loudly (`docs/PHASE5_PRODUCTION.md` §6). TLS terminates at
  the edge (load balancer / ingress) until Phase 6 ships in-app TLS.
  Do not front the app with a second TLS-then-plaintext hop and call it
  end-to-end encryption.
- **Auth, rate limiting, backpressure, caps:** all Phase 6 resilience work
  (§8.3; `docs/PHASE5_PRODUCTION.md` §6). The app enforces request limits
  only (8 KiB headers, 1 MiB bodies) and exact-match routing — nothing more.
- **Status codes, HTTP/2, replication/failover, metrics/tracing, audit
  enforcement, sandboxing, transactions, cancellation:** each explicitly
  deferred into Phase 6 (`docs/PHASE5_PRODUCTION.md` §6). The pipeline
  documents their absence; it MUST NOT reimplement them ad hoc.
- **No orchestrator lock-in:** nothing in §§3–5 requires a specific
  platform, agent, or vendor backend. Edge TLS and the log collector are
  the only platform-provided pieces this draft assumes.

## 7. Open items (Phase 6 decides)

- Exact cross-compilation target matrix and the static-link recipe
  (per-target `.nvc` outputs, §8, are the unit this matrix governs).
- The official base image (name + digest) and its refresh cadence.
- OTel export shape (blessed package, never a vendor mandate, per §8.1).
- End-to-end package signing enforcement and the vulnerability-DB story
  for `noct audit` (§8.2 + exit criteria).

## 8. Compiled artifacts (`.nvc`, Proposed — M5 at the earliest)

`.nvc` is the linkable compiled-package artifact (STYLE_GUIDE.md
§6.7): what a dependency ships when its `.nv` stays private.
Executables remain the final linked product — `noct build` keeps
emitting the platform binary (`-o`, entry-stem default); `.nvc`
is the unit libraries distribute in, not a second executable kind.
The working parallel is Flutter's `app.so`: one compiled module
per target, found in build outputs and consumed at package/run
time rather than compiled from source at use time.

- **Location**: `.noct/build/<target-triple>/<name>.nvc` (proposed;
  `.noct/` is already the toolchain-owned tree alongside
  `.noct/cache/` and `.noct/packages/`). Never committed
  (gitignored), never packed — `publish` collects `*.nv` plus the
  manifest, so build outputs cannot leak into source tarballs.
- **Container v1**: magic + format version, compiled code for one
  target triple, mode tags, package name/version, content hash
  (`sha256:<hex>`, the P-003 §5 format), signature slot (Ed25519,
  the P-003 §7 playbook: domain-separated payload, TOFU with a
  paper trail). Unknown future versions fail loudly on read —
  never best-effort parsed.
- **Producer**: the direct Cranelift backend (Phase 3 track), via
  `noct build --emit-nvc` — the cargo piggyback stays the default
  path until the direct backend is differential-clean against it.
  The registry keeps shipping source tarballs (`pkg.bin`) by
  default; indexed `.nvc` is the later closed-distribution option,
  gated on the interface story below, not a replacement.
- **Security posture**: ships instead of source (no plaintext logic
  to copy) with hash + signature for integrity. That is deterrence,
  not immunity — native code disassembles, so no document promises
  reverse-engineering-proof output, and obfuscation is explicitly
  out of scope for v1.
- **Interface dependency**: a closed `.nvc` is unusable without the
  `.nvir` interface half (NIR.md §7.2) — consumers compile against
  signatures they cannot see into. The two ship together or not at
  all.
- **Non-goals for v1**: `noct run` on `.nvc` directly (fast path,
  later), WASM-target `.nvc` (M6, with the third backend),
  registry-default compiled distribution.
